# WGDB V1 decisions

## Accounts and permissions

- No open registration.
- Admin creates accounts.
- Roles: `user`, `admin`.
- All authenticated users may create/edit movies.
- All authenticated users may create/edit people, genres, countries, languages and studios.
- Admin additionally manages users/roles/activation, restore/hard-delete and review moderation.

## Movie deletion

- Normal delete = soft delete.
- Admin restore supported.
- Permanent delete is admin-only and only allowed after soft delete.

## Ratings/reviews

- Internal user rating: integer `0–100`.
- UI: 0–5 white **Bricks**, nearest half Brick, plus small numeric score.
- Community score = mean of non-null user ratings.
- Watched and favorite are independent booleans.
- No `watched_at` in V1.
- One review per user/movie; review may exist without rating.

## Authentication

- Username or email + password.
- Argon2 password hashes.
- JWT access token in `HttpOnly` cookie.
- `SameSite=Lax`; `Secure=true` in production.
- Double-submit CSRF token for mutating requests.

## Data model

- UUIDv7 generated by Python for local primary keys.
- TMDB/IMDb identifiers are optional external IDs, never primary keys.
- Person is role-neutral; cast/crew credits live in `MoviePerson`.
- Shared classifications are normalized tables.
- External rating values retain their native scales.
- Audit entity IDs are deliberately not foreign keys so hard-delete history survives.

## Import

- TMDB import is optional convenience, not the core identity model.
- Manual film creation must always remain possible.
- Legacy Excel IDs are import mapping only.
- Suspicious workbook values are warnings/overrides, not silently guessed corrections.
- Old personal ratings/watched values remain pending until their owner is explicitly known.

## Production deployment

- Container runtime: Podman.
- Production application containers run rootless under a dedicated Linux user.
- Production lifecycle/orchestration: systemd Quadlet, not Kubernetes.
- nginx is the chosen reverse proxy.
- nginx + Certbot run on the host; application containers expose only loopback high ports.
- PostgreSQL runs in a rootless container with a persistent named volume.
- PostgreSQL is not published to the host network.
- Alembic migrations are explicit deployment steps, not automatic on every backend restart.
- Daily local pg_dump backups are automated; an off-VM backup target remains to be selected.
- Local integration may use `podman compose`; it is not the production orchestrator.
